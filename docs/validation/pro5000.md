# Validation on `pro5000`

Date: 2026-11-20. Access: `ssh pro5000` (root inside a Docker container).

## Host

| Resource | Observed |
|---|---|
| OS / kernel | Alibaba Cloud Linux 3, `5.10.134-19.3.1.al8.x86_64` |
| CPU / RAM | 256 vCPU, ~1.5 TiB |
| GPUs | 8× NVIDIA RTX PRO 5000 72GB Blackwell, driver 580.159.03, CUDA 13.2 |
| Rust | 1.99.0 (installed already) |
| RDMA | no device exposed |

Installed for the verbs build:

```sh
dnf install -y libibverbs-devel librdmacm-devel pkgconf-pkg-config
```

This installed rdma-core 48.0 (`libibverbs 1.14.48.0`), but it does not create a
device in the container.

The discovery output includes:

        memory_mib=73415  flops=395520000000  rdma=false

## RDMA: real Soft-RoCE test passed

The ordinary `pro5000` container is not privileged and does not expose RDMA:

- `/sys/class/infiniband` and `/dev/infiniband` are empty;
- `lspci` shows only a Red Hat `virtio` NIC, no Mellanox/ConnectX/Broadcom RDMA
  function;
- `/lib/modules/$(uname -r)` is not mounted;
- the container lacks `CAP_NET_ADMIN` and `CAP_SYS_MODULE`;
- `modprobe rdma_rxe` reports `Module rdma_rxe not found`;
- `rdma link add rxe0 type rxe netdev eth0` reports `Operation not permitted`.

The **host kernel does support `rdma_rxe`** (dmesg showed it loaded/unloaded
earlier). We used the accessible Docker socket to start a short-lived privileged
helper container with host `/sys`, `/dev`, `/lib/modules`, and the repository
mounted. Inside it:

```sh
modprobe rdma_rxe
rdma link add rxe0 type rxe netdev eth0
rdma link show                 # rxe0 ACTIVE, netdev eth0
ls /sys/class/infiniband       # rxe0
ls /dev/infiniband             # uverbs0
```

The image's `/usr/local` rdma-core 58 lacks the rxe provider, while the system
rdma-core 48 does. After exposing the system `librxe-rdmav34.so` and
`libibverbs.so.1` from the dnf-installed set:

```text
LD_LIBRARY_PATH=/work/rdma-lib IBV_DRIVERS=rxe   /work/plait-node rdma-selftest

plait rdma: rxe0 loopback write/read passed (128 bytes)
```

This is a real two-QP RC loopback: registered MRs, one-sided `RDMA_WRITE`, one
CQ completion, then one-sided `RDMA_READ`, with data verification. The helper
container was removed after the test.

The ordinary `pro5000` container still reports the expected skip because the
device is not exposed to it. To run the node itself over RDMA, start it in the
privileged host class or pass `--device /dev/infiniband` and the rxe link.

## What this validates

- heterogeneous device discovery and capability scheduling on real NVIDIA GPUs;
- replicated `DeviceProfile` and `Compute` placement through the EPaxos runtime;
- all EP/DP/PP/DSA reference runners on a remote machine;
- the RDMA build path against rdma-core 48 and 55;
- real Soft-RoCE two-QP `RDMA_WRITE` + `RDMA_READ` with data verification.

It does **not** validate vendor kernel execution or multi-host RDMA traffic.
